# Git 작업 규칙

저장소 Git·버전·작업 마무리 보고에 적용한다.

## 브랜치

- 기본 브랜치는 `main` 이다.
- 작은 수정은 `main` 에서 커밋·push 해도 된다.
- 하네스(`.ai`, `AGENTS.md`)와 앱 코드(`backend`, `frontend` 등)를 크게 바꾸거나, 여러 날에 걸친 작업은 `feature/짧은-설명` 브랜치에서 진행한 뒤 `main` 에 merge 하고 push 한다.

## 커밋

- 한 커밋은 하나의 논리적 변경이다. 커밋 메시지는 **왜** 바꿨는지 한두 문장으로 적는다.
- 가능하면 하네스 변경과 앱 코드 변경을 한 커밋에 섞지 않는다 (같은 작업에서 불가피하면 예외).
- **push** 는 **사용자가 요청할 때만** 한다. push·커밋(create) **전** `AGENTS.md` 「하네스·일관성 검증」「Push (사용자 push 요청 시)」— **기계 `check.sh` + 전체 수동 점검 (1~6)**. grep·diff만으로 수동을 대체하지 않는다.

## 버전 (Git · 앱)

API URI 의 `/v1` 과는 별개이다. 여기서 말하는 버전은 **저장소·앱이 어느 시점의 산출물인지** 구분하는 것이다.

- 커밋마다 Git 이력에 변경이 쌓인다. push 할 때마다 GitHub 에 그 시점이 남는다.
- “무엇이 바뀌었는지”는 커밋 메시지와 diff 로 본다.
- 하네스·폴더 구조·여러 앱을 묶은 **마일스톤**이 있으면 Git **tag** 로 표시한다 (예: `v0.1.0`, `v0.2.0`).
- semver `주.부.패치` — 주=큰 방향 변경, 부=기능 추가, 패치=버그·소규모 수정.
- 태그는 모든 커밋마다 붙이지 않는다. “데모 가능”, “하네스 1차 완료” 같은 구간에만 붙인다.
- `backend/java/...`, `frontend/...` 처럼 **실행 가능한 앱**이 생기면, 그 앱 폴더 안에 **앱 전용 버전**을 둔다 (Java: `build.gradle`, React: `package.json`).
- 앱 버전은 **그 앱만** 올린다. 다른 앱·하네스와 숫자를 맞출 필요 없다.
- 앱을 배포·데모할 만한 상태가 되면 앱 버전을 올리고, 필요하면 저장소 tag 도 함께 붙인다.

### 사실

| 구분 | 어디 | 예 |
| --- | --- | --- |
| 변경 이력 | Git commit / push | 매 작업 |
| 저장소 마일스톤 | Git tag (루트) | `v0.1.0` |
| 앱 릴리스 | 앱 빌드 설정 | `1.2.0` |

## 하지 않는 것

| 금지 | 내용 |
| --- | --- |
| 이력 파괴 | `git reset --hard`, force push, 이미 올린 커밋 이력을 지우는 조작 |
| 커밋 | 사용자가 요청하지 않은 커밋 생성 |
| 범위 | 사용자가 요청하지 않은 파일 수정·되돌리기 |
| 포맷 | 이번 변경과 관련 없는 파일의 포맷팅·정렬 |

되돌리기나 이력 정리가 필요하면 먼저 알리고 동의를 받는다.
